# 一种端侧视频流背景特效处理方法、装置、设备及存储介质

## 一、说明目前同类技术应用的现状及缺陷

### 1.1 现有产品或者方法的结构、流程及工作过程

实时视频会议、在线课堂、远程答辩、远程办公和即时通信视频通话中，背景虚化、虚拟背景和背景移除已经成为较常见的视频增强功能。公开资料显示，Google Meet 等会议产品已经采用基于 Web 机器学习的背景虚化和背景替换能力；MediaPipe Selfie Segmentation 面向“自拍效果”和“视频会议”等近距离人像场景，可在手机和笔记本上实时分割画面中的主要人物；WebRTC Insertable Streams、MediaStreamTrack Processor、Canvas captureStream 等浏览器能力也被用于在视频流发送前对帧进行处理。这些资料说明，同类技术的基本方向已经从单纯的视频显示增强，逐步发展为“端侧分割、端侧合成、再接入实时通信链路”的实时视频处理流程。

从现有产品或方法的技术结构看，同类方案通常包括如下功能模块。

第一，媒体采集模块。该模块通过摄像头采集用户本地视频，通过麦克风采集音频，并将采集到的媒体轨道交给 WebRTC、SFU 或 P2P 通信模块。对于 Web 会议系统，该模块一般依赖浏览器的 `getUserMedia` 接口，并由页面或业务框架维护音视频开关、设备切换和媒体轨道生命周期。

第二，人像分割模块。该模块用于识别视频帧中人物区域和背景区域。现有方案常见做法是使用 TensorFlow.js、MediaPipe、ONNX Runtime Web、TFLite WebAssembly 或浏览器原生背景处理 API，对低分辨率视频帧进行推理，输出一个前景概率掩码。该掩码通常表示每个像素属于人物前景的概率，后续背景虚化和背景替换都依赖该掩码完成前景与背景的区分。

第三，图像合成模块。该模块根据分割掩码对视频帧进行背景处理。背景虚化通常需要对原视频帧进行模糊处理，再保留人物前景；背景替换通常需要将用户选择的图片、视频或纯色背景与原始人物前景进行融合。常见实现方式包括 Canvas 2D 像素处理、WebGL 纹理渲染、WebGPU 计算、WebAssembly 像素计算或上述方式的组合。

第四，流接入模块。该模块将处理后的画面重新接入实时通信系统。一些方案仅在本地页面显示处理结果；另一些方案会通过 `canvas.captureStream()`、Insertable Streams 或 MediaStreamTrack Processor 将处理后的帧作为新的发送源，使远端参与者看到背景特效画面。

第五，用户交互模块。该模块提供背景虚化、背景替换、背景图选择、自定义背景上传、关闭效果等交互入口。较完善的产品还需要处理屏幕共享、摄像头关闭、摄像头切换、会议离开、网络质量变化等状态。

现有软件方案的一般工作流程可以概括为：用户进入会议并开启摄像头；系统获取摄像头视频流；将视频帧缩放至模型输入尺寸；人像分割模型输出前景掩码；图像合成模块依据掩码生成背景虚化或背景替换画面；将合成画面显示到本地页面，或者捕获为新的媒体轨道后发送给远端。对于服务端处理方案，终端还会先上传原始视频流，由服务端执行分割与合成后再分发；对于原生客户端方案，分割和合成通常在客户端本地以 C++、Metal、OpenGL、DirectX、CUDA 或平台原生图像处理能力完成；对于浏览器方案，分割和合成一般在 JavaScript、WebAssembly、WebGL 或 WebGPU 中完成。

结合当前项目的端侧视频流特效处理模块，已有实现主要分布在 `wasm/src/lib.rs`、`frontend/src/composables/useMedia.js` 和 `frontend/src/features/meeting/views/MeetingRoom.vue` 中。其中，`useMedia.js` 负责媒体采集、会议连接、ONNX Runtime Web 推理、WebAssembly 模块初始化、输出画布创建、特效流启停、视频生产者轨道替换和状态管理；`lib.rs` 负责编译为 WebAssembly 后执行掩码增强、背景虚化和背景替换等像素级处理；`MeetingRoom.vue` 负责在会议页面中提供背景效果选择、预设背景选择、自定义背景上传、状态提示和屏幕共享互斥控制。

当前项目的端侧处理流程可以描述为：终端加入会议后，先通过媒体服务分配 SFU 节点并建立 WebRTC 发送与接收传输；系统获取本地摄像头与麦克风，发布普通音视频轨道；当用户选择背景虚化或背景替换后，系统初始化 WebAssembly 模块和 ONNX 分割模型，克隆当前摄像头轨道并绑定到隐藏视频元素；推理循环将隐藏视频元素帧绘制到低分辨率离屏画布，生成 256×144 的前景概率掩码；渲染循环将视频帧绘制到 640×360 的处理画布，将视频帧和掩码写入 WebAssembly 线性内存，由 WebAssembly 模块进行掩码平滑、上采样、联合双边滤波和背景合成；处理结果写回输出画布；输出画布通过 `captureStream(30)` 生成特效视频轨道；系统通过视频生产者的 `replaceTrack` 将普通摄像头轨道替换为特效轨道，远端参与者看到处理后的背景特效画面。

从硬件支持角度看，该类软件方案通常运行于带有摄像头、麦克风、CPU、内存、图形渲染能力和现代浏览器的终端设备。终端可以是笔记本电脑、台式机、平板电脑或智能手机。若浏览器支持 WebAssembly、OffscreenCanvas、Canvas 2D、WebGL2、WebRTC 和媒体设备接口，系统即可运行基本功能；若浏览器支持跨源隔离和多线程 WebAssembly，模型推理或部分计算可以进一步获得性能提升。当前项目采用的实现并不依赖专用硬件或云端 GPU，主要利用浏览器运行时、WebAssembly 线性内存和 WebRTC 媒体轨道替换能力完成端侧处理。

### 1.2 现有技术的所有缺点及本发明要解决的技术问题

现有同类技术虽然已经能够实现背景虚化、虚拟背景或背景移除，但在 Web 实时会议系统中仍存在较多工程问题。本发明需要正面解决以下技术问题。

第一，服务端处理成本高。若背景处理在服务器完成，服务端需要接收原始视频、解码视频帧、运行分割模型、执行背景合成、重新编码并分发视频。多人会议下，每一路视频都可能产生额外算力消耗，服务器 CPU、GPU、内存和带宽压力明显增加。该问题会直接导致部署成本高、扩容成本高，并限制系统在较大规模会议场景下的并发能力。因此，本发明要解决的技术问题之一是：如何在不增加服务端背景处理负担的情况下，在终端侧完成实时背景特效处理。

第二，原始背景隐私暴露风险高。用户开启背景虚化或虚拟背景的主要目的通常是隐藏真实环境。如果先将原始视频上传到服务器再处理，则服务端处理链路仍可能接触未处理的真实背景画面。即使系统承诺不存储，也扩大了隐私暴露面。因此，本发明要解决的技术问题之一是：如何使终端在上传前完成背景处理，减少原始背景画面离开终端的机会。

第三，浏览器端纯 JavaScript 像素处理速度慢且稳定性不足。背景虚化和背景替换都需要对每帧大量像素进行遍历。以 640×360 分辨率为例，每帧包含 230400 个像素；若处理分辨率为 640×480，则每帧包含 307200 个像素。掩码上采样、灰度计算、边缘滤波、背景模糊和 alpha 混合均为高频计算。如果这些逻辑全部由 JavaScript 数组循环实现，容易受解释执行、垃圾回收和主线程调度影响，导致帧耗时升高和输出抖动。因此，本发明要解决的技术问题之一是：如何将计算密集型像素处理转移到更适合连续内存计算的执行环境中，并减少每帧对象分配。

第四，低分辨率分割掩码直接合成效果差。为了满足实时性，端侧人像分割模型常采用低分辨率输入输出。低分辨率掩码若直接放大到视频分辨率，会导致人物轮廓边缘出现台阶、毛刺、抖动、背景侵入前景或前景外溢。头发、肩部、手部等边缘区域尤其容易产生明显瑕疵。因此，本发明要解决的技术问题之一是：如何对低分辨率分割掩码进行时域稳定和空间边缘优化，使合成边缘更贴合人物真实轮廓。

第五，背景虚化计算量大。真实背景虚化通常需要较大模糊半径。若采用直接二维卷积，计算复杂度随核面积增长，难以满足 30fps 会议场景的帧预算。若简单降低模糊强度，隐私保护和视觉效果又会下降。因此，本发明要解决的技术问题之一是：如何采用适合端侧实时计算的背景模糊方式，在视觉效果和计算开销之间取得平衡。

第六，特效启停容易造成会议视频中断。部分实现会在开启特效时关闭原视频生产者、重新创建视频流或重新协商 WebRTC 连接。该过程可能导致远端画面短暂黑屏、订阅关系变化、服务端统计异常或会议状态不同步。因此，本发明要解决的技术问题之一是：如何在不重建房间连接、不重建传输层、不破坏远端订阅关系的情况下，将普通摄像头流平滑切换为背景特效流。

第七，背景特效与屏幕共享存在状态冲突。会议中视频生产者可能承载摄像头视频，也可能承载屏幕共享视频。如果用户在屏幕共享期间开启背景特效，或者在背景特效启用时启动屏幕共享，容易出现发送轨道来源混乱、页面状态显示错误或远端接收异常。因此，本发明要解决的技术问题之一是：如何建立背景特效与屏幕共享之间的互斥和恢复机制。

第八，摄像头设备切换与特效轨道恢复复杂。用户可能在会议中切换摄像头设备。如果特效模块继续引用旧摄像头轨道，可能导致隐藏视频元素无画面、推理循环异常、输出画布停止更新或关闭特效后无法恢复普通摄像头。因此，本发明要解决的技术问题之一是：如何在设备切换时正确停止特效、释放旧轨道并替换新轨道。

第九，资源释放不彻底会造成性能下降。背景特效运行过程中涉及隐藏视频元素、克隆轨道、离屏画布、输出画布、推理会话、WebAssembly 处理器、动画帧、定时器和媒体流。如果会议离开或特效关闭时未完整释放，浏览器仍可能持续占用摄像头、CPU 和内存。因此，本发明要解决的技术问题之一是：如何对端侧背景处理资源进行统一生命周期管理。

第十，现有方案的功能模块边界不清晰，难以与会议业务稳定融合。一些背景处理示例仅关注视觉效果演示，未充分考虑 SFU 会议、主持人控制、参与者状态、本地预览、远端发布、网络统计和用户交互之间的关系。因此，本发明要解决的技术问题之一是：如何将背景特效处理模块作为会议系统的一部分，使其与现有媒体发布、参与者状态和页面交互协同工作。

### 1.3 缺点类型归纳

从成本角度看，服务端背景处理会显著增加服务器算力成本、带宽成本和部署复杂度；原生客户端方案则增加多平台开发、安装和升级成本。

从响应速度角度看，服务端处理需要经历上传、服务端处理和重新分发，端到端链路更长；浏览器端纯 JavaScript 像素处理则容易因主线程阻塞造成帧率下降。

从效果角度看，低分辨率掩码直接使用会导致人物边缘不自然，背景虚化或替换区域容易闪烁，用户感知质量不稳定。

从使用便利性角度看，要求安装原生客户端会降低用户进入会议的便利性；要求用户手动重启视频或重新入会才能应用背景特效，也不符合实时会议场景中的交互习惯。

从稳定性角度看，特效启停、屏幕共享、摄像头切换和会议离开之间若缺少统一控制，会导致媒体轨道泄漏、远端画面中断、状态显示错误和资源占用持续增加。

从隐私角度看，云端或服务端处理原始视频会使真实背景先离开终端，不能充分满足用户希望在本地隐藏环境信息的需求。

本发明正是针对上述成本高、响应慢、效果差、使用不方便、稳定性不足和隐私暴露等问题提出改进方案。

## 二、本发明或者实用新型的整体构思

本发明的整体构思是：在终端浏览器侧建立一条独立于原始摄像头采集但可无缝接入会议发送端的视频背景特效处理链路。该链路以本地摄像头轨道为输入，以输出画布捕获的视频轨道为输出，将人像分割、掩码增强、背景虚化、背景替换和媒体轨道替换统一纳入会议媒体控制流程。

本发明基于以下目的对现有技术进行改进。

第一，为降低服务端成本和保护用户隐私，将背景处理从服务端前移到终端侧。终端在视频上传前完成背景虚化或背景替换，服务端只接收处理后的特效视频流并按普通视频流进行转发。

第二，为提高浏览器端实时处理性能，将计算密集型像素处理从通用 JavaScript 逻辑中剥离，交给 WebAssembly 模块执行。JavaScript 侧主要负责媒体状态、模型推理调度、画布调度和 WebRTC 轨道替换；WebAssembly 侧主要负责连续内存中的掩码增强和像素合成。

第三，为改善低分辨率人像分割带来的边缘问题，在背景合成前增加掩码增强流程。该流程不是简单地将掩码放大，而是依次执行低分辨率时域平滑、双线性上采样、原始视频灰度缓存计算和联合双边滤波，使掩码在时间上更稳定、在空间上更贴近人物边缘。

第四，为降低启停特效对会议连接的影响，本发明不重新创建会议房间连接、不重新创建 SFU 传输层，也不要求远端重新订阅视频，而是通过输出画布生成特效视频轨道，并用 `replaceTrack` 替换既有视频生产者的轨道。这样可以保持生产者标识、远端消费者订阅关系和会议状态连续。

第五，为解决复杂会议交互中的状态冲突，本发明把背景特效作为媒体状态机的一部分处理。屏幕共享期间禁止背景特效；启动屏幕共享前自动关闭背景特效；切换摄像头设备前停止特效；关闭特效后恢复原摄像头轨道；离开会议时释放所有特效资源。

本发明具体改进的部分包括：低分辨率掩码到目标处理分辨率掩码的增强方式；WebAssembly 线性内存中的帧、掩码、背景和输出缓冲区复用方式；背景虚化和背景替换的像素合成方式；输出画布到 WebRTC 视频生产者的轨道替换方式；背景特效与会议业务状态之间的互斥和资源释放方式。

## 三、本发明或者实用新型技术方案的详细阐述

### 3.1 总体技术方案

本发明提供一种端侧视频流背景特效处理方法。该方法包括如下步骤。

步骤S1，终端加入会议并获取本地摄像头视频流。系统通过媒体服务分配 SFU 节点，建立信令连接，加载路由能力，创建发送传输和接收传输，并通过浏览器媒体设备接口获取摄像头轨道和麦克风轨道。摄像头轨道作为普通视频轨道先发布到会议中，以保证用户进入会议后可立即通信。

步骤S2，初始化端侧背景特效资源。系统加载 WebAssembly 模块，创建 WebAssembly 图像处理器，配置端侧人像分割推理运行时，加载人像分割模型，并创建掩码离屏画布、处理离屏画布和输出画布。系统还缓存 WebAssembly 线性内存中输入帧缓冲区、掩码缓冲区、输出帧缓冲区和背景缓冲区对应的 TypedArray 视图，避免在每帧处理时重复创建大对象。

步骤S3，克隆摄像头轨道并创建隐藏视频源。当用户启用背景虚化或背景替换时，系统获取当前视频生产者中的摄像头轨道，保存该轨道作为后续恢复来源，并克隆一条轨道绑定到隐藏视频元素。隐藏视频元素不显示在页面上，仅供分割推理和帧处理读取视频帧。

步骤S4，生成低分辨率前景概率掩码。推理循环将隐藏视频元素的当前帧绘制到 256×144 的掩码离屏画布，读取像素数据并归一化为模型输入张量。端侧分割模型输出背景和前景通道后，系统对每个像素计算前景概率，形成低分辨率掩码。

步骤S5，在 WebAssembly 中增强掩码。系统在渲染循环中将当前视频帧写入 WebAssembly 输入缓冲区，将最近一次生成的低分辨率掩码写入掩码缓冲区，调用 WebAssembly 掩码准备函数。该函数在 WebAssembly 内依次执行低分辨率时域平滑、双线性上采样、灰度缓存计算和联合双边滤波，生成目标处理分辨率下的增强掩码。

步骤S6，执行背景虚化或背景替换。若用户选择背景虚化，WebAssembly 模块先对输入视频帧执行可分离盒型模糊，生成模糊背景帧，再按照增强掩码对原始帧和模糊帧进行逐像素 alpha 混合。若用户选择背景替换，系统先将背景图像按目标处理尺寸裁剪缩放并写入 WebAssembly 背景缓冲区，再按照增强掩码对原始帧和背景帧进行逐像素 alpha 混合。

步骤S7，将特效帧输出到画布。WebAssembly 输出缓冲区中的 RGBA 数据被封装为图像数据并写回处理画布，随后绘制到输出画布。输出画布作为特效画面的唯一发布源和本地预览源。

步骤S8，捕获输出画布并替换视频发送轨道。系统调用输出画布的捕获接口生成媒体流，取得其中的视频轨道，并将该轨道通过视频生产者的轨道替换接口接入会议发送端。远端参与者无需重新订阅，即可接收处理后的背景特效视频。

步骤S9，按照会议状态进行恢复与释放。当用户关闭背景特效、切换背景、开启屏幕共享、切换摄像头、关闭摄像头或离开会议时，系统根据状态机执行对应的停止、恢复、重新加载或释放流程。

### 3.2 媒体采集与会议发布改进

本发明的第一处改进是将背景特效处理接入既有会议媒体发布流程，而不是作为独立页面效果存在。

在普通会议流程中，终端加入房间后获取本地媒体流，并将音频轨道和视频轨道分别发布到 SFU。当前项目中，视频轨道发布时可以配置 Simulcast 编码参数，使 SFU 和远端消费者能够根据网络情况选择不同空间层。背景特效启用后，本发明不改变房间、传输层和远端订阅关系，而是对同一个视频生产者执行轨道替换。

具体改进方式为：系统在启用特效时获取当前视频生产者，读取其原始摄像头轨道并保存；通过输出画布捕获生成特效视频轨道；调用视频生产者的 `replaceTrack` 方法，将生产者内部承载的轨道从原始摄像头轨道替换为特效视频轨道；同时在生产者的应用数据中标记视频来源为 `effect`，并记录特效类型为 `blur` 或 `replace`。关闭特效时，系统再将生产者轨道替换回保存的原始摄像头轨道；若原始轨道已经失效，则重新请求摄像头并使用新轨道替换。

该改进的技术效果是：会议连接不中断，远端消费者不需要重新订阅，会议系统的参与者列表、主持人控制、网络统计和视频生产者标识可以保持连续。相比重新创建视频生产者或重新协商连接，该方式明显降低了特效启停对会议体验的影响。

### 3.3 端侧分割推理改进

本发明的第二处改进是将人像分割推理设置为独立异步循环，并采用低分辨率输入降低模型计算压力。

具体实现时，系统创建尺寸为 256×144 的掩码离屏画布。推理循环只负责将隐藏视频元素当前帧绘制到该画布，读取像素并归一化后送入端侧 ONNX 模型。模型输出后，系统计算前景概率掩码并保存为当前掩码。推理循环设置并发保护标志，若上一轮推理尚未结束，则延后下一轮推理，避免多个推理任务堆积占用浏览器主线程和 WebAssembly 推理运行时资源。

该改进不是简单调用模型，而是将推理循环与渲染循环解耦。渲染循环可以使用最近一次可用掩码进行合成，不必等待每一帧都完成模型推理。这样，在模型推理出现短时波动时，输出画布仍可继续根据上一帧或最近掩码进行渲染，配合时域平滑减少画面突变。

该改进解决的问题是：模型推理速度可能低于显示刷新速度，如果强制每帧等待推理完成，会导致背景特效帧率下降；如果并发启动多个推理任务，则会造成 CPU 占用升高和延迟累积。独立异步推理循环在实时性和资源占用之间取得平衡。

【图7占位：推理循环与渲染循环解耦示意图。建议绘制推理循环输出 currentMask，渲染循环读取最近 currentMask。】

### 3.4 WebAssembly 缓冲区和内存复用改进

本发明的第三处改进是通过 WebAssembly 线性内存和固定缓冲区复用来执行计算密集型像素处理。

WebAssembly 图像处理器初始化时，按目标处理分辨率创建输入帧缓冲区、输出帧缓冲区、背景缓冲区、上采样掩码缓冲区、灰度缓存、滤波中间缓冲区、模糊中间缓冲区和若干通道累加缓冲区。同时按固定分割尺寸创建低分辨率掩码缓冲区和上一帧掩码缓冲区。JavaScript 侧通过 WebAssembly 暴露的指针创建 TypedArray 视图，例如输入帧对应 Uint8Array，掩码对应 Float32Array，输出帧对应 Uint8ClampedArray。只要 WebAssembly 内存不增长，这些视图可以在整个特效会话中复用。

每帧处理时，JavaScript 侧只执行必要的数据写入：将处理画布当前帧数据写入输入缓冲区，将当前低分辨率掩码写入掩码缓冲区；背景替换时，背景图像只在加载或切换时写入背景缓冲区，不在每一帧重复写入。WebAssembly 模块在内部直接读取和写入连续内存，减少跨语言调用次数和临时对象创建。

该改进解决的问题是：浏览器端逐帧处理如果频繁分配数组、复制对象或创建 ImageData，会增加垃圾回收和主线程抖动。通过固定缓冲区复用，系统能够使每帧处理路径更稳定，便于维持会议场景下的持续运行。

### 3.5 掩码时域平滑改进

本发明的第四处改进是在低分辨率掩码空间执行时域平滑。

模型输出的前景概率掩码可能在相邻帧之间发生小幅波动，尤其在头发、手部、肩膀边缘、光照变化和运动模糊场景下更明显。若直接使用该掩码进行合成，背景和人物边界会出现闪烁。本发明在 WebAssembly 模块中保存上一帧平滑后的低分辨率掩码，并对当前掩码执行指数移动平均。例如，对于同一掩码像素，平滑结果可表示为：当前平滑值等于当前模型概率乘以平滑系数，再加上一帧平滑值乘以剩余系数。当前项目实现中，平滑系数可设为 0.7。

将时域平滑放在低分辨率空间具有两个实际好处：一是计算量小，256×144 掩码仅包含 36864 个概率值，远低于目标视频分辨率；二是先稳定掩码再上采样，可以避免上采样后对大量像素重复执行同类时间平滑计算。

该改进解决的问题是：分割模型输出在时间上不稳定，导致背景特效边缘抖动。通过低分辨率指数移动平均，系统可在较低计算成本下提升视频连续性。

### 3.6 掩码上采样与联合双边滤波改进

本发明的第五处改进是将低分辨率掩码转换为目标处理分辨率掩码时，不仅执行上采样，还结合原始视频边缘进行联合双边滤波。

首先，WebAssembly 模块对低分辨率掩码进行双线性上采样。对于目标处理分辨率中的每个像素，计算其对应到低分辨率掩码坐标系的位置，并取周围四个掩码值按距离插值。该步骤避免最近邻放大造成的块状边缘。

其次，WebAssembly 模块根据输入视频帧计算灰度缓存。对每个像素读取红、绿、蓝通道，按人眼亮度敏感程度加权得到灰度值。该灰度缓存代表原始视频中的边缘和纹理信息。

再次，WebAssembly 模块对上采样掩码执行联合双边滤波。滤波时，对于中心像素周围邻域中的每个像素，综合考虑空间距离和灰度差异。空间距离越近，权重越高；灰度越接近，颜色相似度权重越高；若邻域像素与中心像素灰度差异较大，说明可能跨越了人物边缘或背景边缘，其掩码值对中心像素的影响会被削弱。最终，系统根据综合权重对邻域掩码值加权求和，得到边缘保持的增强掩码。

该改进不是普通的掩码模糊。普通模糊会在人物边缘两侧无差别扩散前景概率，容易造成背景渗入人物或人物边缘过宽。联合双边滤波利用原始视频灰度边缘约束掩码扩散，使掩码边界更贴合实际人物轮廓。

该改进解决的问题是：低分辨率掩码直接放大边缘粗糙，简单平滑又会降低边界准确性。通过双线性上采样和联合双边滤波组合，系统在实时性和边缘质量之间取得平衡。

### 3.7 背景虚化改进

本发明的第六处改进是采用适合实时处理的可分离盒型模糊生成背景虚化帧，并通过增强掩码进行前景保留。

背景虚化分两部分完成：第一部分生成模糊帧，第二部分进行前景与模糊背景混合。

生成模糊帧时，WebAssembly 模块先将输入帧复制到模糊缓冲区。然后执行水平方向模糊：对每一行分别构建红、绿、蓝通道的前缀和，利用前缀和在 O(1) 时间内计算每个像素左右半径范围内的均值。随后执行垂直方向模糊：对每一列维护滑动窗口累加值和计数，随着行坐标移动逐步移除窗口顶部行并加入底部行，计算上下半径范围内的均值。水平和垂直两次处理构成一轮可分离盒型模糊。

前景与模糊背景混合时，WebAssembly 模块读取增强掩码中的前景概率。前景概率越高，输出越接近原始摄像头帧；前景概率越低，输出越接近模糊帧；边缘区域按概率平滑过渡。为提高效率，前景概率可转换为 0 至 256 的整数权重，再使用整数乘加和位移完成 RGB 通道混合。

该改进解决的问题是：直接大核卷积计算量过高，难以实时运行。可分离盒型模糊将模糊计算复杂度控制为与像素数线性相关，并且前缀和和滑动窗口都适合 WebAssembly 连续内存遍历。虽然该方式是对高斯模糊的近似，但在会议背景虚化场景中具有可接受的视觉效果和较好的实时性。

### 3.8 背景替换改进

本发明的第七处改进是将背景图像预处理后写入 WebAssembly 背景缓冲区，并在每帧中直接进行线性混合。

用户可以选择预置背景，也可以上传自定义背景。系统在上传自定义背景时进行文件类型和大小校验，例如仅允许图片文件，并限制文件大小不超过预设阈值。背景图加载成功后，系统创建与目标处理分辨率一致的离屏画布，将背景图按 cover 模式绘制到画布中。cover 模式通过取宽高比例中的较大缩放系数，使背景图铺满画面，再居中裁剪多余部分，避免背景被拉伸变形或出现空白边。

背景图像绘制完成后，系统读取该离屏画布的 RGBA 像素数据，并写入 WebAssembly 背景缓冲区。该写入只在背景图首次加载或用户切换背景时执行。每帧渲染时，WebAssembly 模块读取输入帧、增强掩码和背景缓冲区，根据增强掩码对原始人物前景与背景图像进行逐像素 alpha 混合。

如果用户在背景替换模式下切换背景，本发明不重新创建输出画布，不重新捕获媒体轨道，也不替换视频生产者轨道，而是仅重新加载背景缓冲区。下一帧渲染自然使用新背景。该改进减少了背景切换延迟和媒体流中断风险。

该改进解决的问题是：背景替换若每帧重新读取或缩放背景图，会造成额外计算浪费；若切换背景时重建整个特效流，会影响远端画面连续性。通过背景缓冲区预加载和热切换，系统能够在保持媒体轨道稳定的情况下更新背景。

### 3.9 输出画布、本地预览和远端发布改进

本发明的第八处改进是将输出画布同时作为本地预览源和远端发布源，使用户看到的效果与远端接收内容一致。

在未启用特效时，本地预览可以通过 WebGL 或 Canvas 将本地摄像头流绘制到会议视频网格中。启用特效后，系统将输出画布作为 `localEffectCanvas` 提供给会议页面。会议页面检测到该画布后，将其插入本地视频容器并设置尺寸样式。该画布同时通过 `captureStream(30)` 生成视频轨道发送给远端。

该设计避免了两套不同渲染链路造成的不一致：如果本地预览显示一种画面，而远端实际接收另一种画面，用户难以判断背景特效是否真实生效。本发明让本地预览直接显示输出画布，能够使本地观察结果与远端发布结果保持一致。

此外，输出画布固定为目标处理分辨率，渲染循环通过帧间隔限制接近 30fps 的处理节奏。这样既能满足实时会议的基本流畅性，又避免浏览器以过高频率重复执行重计算。

### 3.10 状态监听与特效切换改进

本发明的第九处改进是为背景特效建立状态监听机制，而不是在每个按钮事件中分散处理媒体轨道逻辑。

系统监听效果类型和所选背景两个状态。当效果类型为 `none` 时，系统停止特效流，并恢复普通摄像头轨道；当效果类型从 `none` 变为 `blur` 或 `replace` 时，系统启动特效流；当效果类型在 `blur` 和 `replace` 之间切换时，系统先停止旧特效，再启动新特效；当效果类型保持 `replace` 而背景图发生变化时，系统只重新加载背景图到 WebAssembly 背景缓冲区。

该改进将特效启停、类型切换和背景切换统一到一个状态机中，减少重复代码和状态遗漏。即使用户通过不同入口改变效果类型，例如点击顶部按钮、侧栏效果卡片或上传自定义背景，底层媒体处理仍由同一监听逻辑负责。

### 3.11 屏幕共享互斥改进

本发明的第十处改进是明确规定背景特效与屏幕共享互斥。

当用户准备开启屏幕共享时，系统先检查背景特效是否处于启用状态，或者效果类型是否不是 `none`。若是，则先停止背景特效，将效果类型恢复为 `none`，并提示用户已关闭背景特效以开始屏幕共享。随后，系统获取屏幕共享轨道，关闭或替换原摄像头视频生产者，并发布屏幕共享轨道。

当用户已经处于屏幕共享状态时，若尝试启用背景虚化或背景替换，系统会拒绝该操作并提示屏幕共享期间不可使用背景特效。该处理在页面交互层和媒体状态监听层均可执行，从而避免用户通过不同入口绕过限制。

该改进解决的问题是：摄像头背景特效与屏幕共享都可能占用同一个视频发送位置，如果不做互斥控制，远端可能收到错误来源的视频，或本地状态显示与实际轨道不一致。

### 3.12 设备切换与恢复改进

本发明的第十一处改进是对摄像头设备切换提供恢复策略。

当用户切换视频设备时，如果背景特效处于启用状态或效果类型不是 `none`，系统先停止特效流并将效果类型恢复为 `none`。随后重新调用浏览器媒体设备接口获取指定摄像头的新视频轨道，将该轨道替换到视频生产者中，并更新本地媒体流和本地预览。

关闭背景特效时，系统优先恢复保存的原始摄像头轨道。如果原始摄像头轨道仍为 live 状态，则直接替换回视频生产者；如果原始轨道已经失效，则重新请求摄像头轨道并替换。这样可以应对摄像头被用户关闭、设备切换、浏览器回收轨道等情况。

该改进解决的问题是：背景特效运行时使用的是克隆轨道和输出画布轨道，若设备变化时不重新协调轨道来源，容易出现隐藏视频元素引用旧轨道、输出画布停止更新或关闭特效无法恢复画面的情况。

### 3.13 资源释放改进

本发明的第十二处改进是对特效相关资源进行集中释放。

停止背景特效时，系统依次停止隐藏视频元素中的克隆轨道，移除隐藏视频元素，取消渲染循环的动画帧，清除推理循环的定时器，将推理状态标志复位，停止输出画布捕获流，恢复视频生产者轨道，重置背景加载标志，并更新本地预览。

离开会议时，系统进一步释放 ONNX 推理会话、WebAssembly 处理器、TypedArray 缓存视图、输出画布、掩码画布、处理画布、本地预览渲染器、远端消费者、本地媒体流和信令连接。释放顺序上，先停止背景特效和循环，再释放模型与 WebAssembly 资源，最后重置会议状态，避免后台循环继续访问已释放对象。

该改进解决的问题是：实时会议持续时间可能较长，用户也可能多次启停特效。如果隐藏视频元素、定时器、动画帧或媒体轨道未释放，会造成 CPU 占用、摄像头占用和内存占用持续增加，影响后续会议体验。

### 3.14 可替代方案

本发明允许在不改变整体构思的前提下采用若干替代方案。

第一，人像分割模型可替换。当前实施例使用 ONNX Runtime Web 加载端侧人像分割模型，替代方案可以使用 MediaPipe Selfie Segmentation、TensorFlow.js BodyPix、WebNN 模型、WebGPU 推理模型或浏览器原生背景分割能力。只要能够输出低分辨率前景概率掩码，即可接入后续 WebAssembly 掩码增强和背景合成流程。

第二，像素处理运行环境可替换。当前实施例使用 Rust 编写并编译为 WebAssembly 的图像处理模块，替代方案可以使用 C、C++、AssemblyScript 或其他语言编译为 WebAssembly；在支持 WebGPU 的终端上，也可以将背景模糊和 alpha 混合迁移到 GPU 计算管线。但无论采用何种实现，都应保留输入帧、掩码、背景和输出缓冲区复用的思想。

第三，媒体流接入方式可替换。当前实施例通过输出画布 `captureStream` 生成特效视频轨道，并通过视频生产者 `replaceTrack` 接入 SFU。替代方案可以使用 WebRTC Insertable Streams 或 MediaStreamTrack Processor/Generator 对视频帧进行变换，也可以在 P2P 通话中对 RTCRtpSender 执行轨道替换。只要能够在不重建会议连接的情况下更新发送源，即可实现本发明目的。

第四，背景虚化算法可替换。当前实施例采用可分离盒型模糊。替代方案可以采用多轮盒型模糊、近似高斯模糊、双边背景模糊、下采样后模糊再上采样或基于 WebGL/WebGPU 的纹理模糊。不同方案可根据终端性能和视觉需求选择。

第五，掩码增强参数可调整。时域平滑系数、联合双边滤波核半径、颜色权重函数、目标处理分辨率、输出帧率和模糊半径均可配置。低端设备可降低处理分辨率或模糊半径，高性能设备可提高分辨率或滤波质量。

第六，背景资源来源可扩展。背景图可以来自本地上传、预置资源、企业统一背景库、远程对象存储或动态视频背景。对于远程背景资源，可在加载前进行跨域校验、格式校验和尺寸限制。

## 四、申请本发明或者实用新型的目的

申请本发明的目的在于对当前项目中已经研发形成的端侧视频流背景特效处理成果进行系统化保护。该成果并非单一的背景虚化按钮或简单的页面视觉效果，而是围绕实时会议场景形成的一套完整技术方案：端侧分割推理、WebAssembly 掩码增强、背景虚化与背景替换、输出画布媒体化、视频生产者轨道替换、会议状态互斥和资源生命周期管理共同构成了可落地的端侧实时视频处理链路。

从研发成果保护角度看，本发明需要保护的核心不只是某一种模型或某一个背景图处理函数，而是以下组合关系：以低分辨率分割模型降低端侧推理成本；以 WebAssembly 线性内存执行掩码增强和像素合成；以时域平滑、双线性上采样和联合双边滤波改善掩码质量；以可分离盒型模糊或背景缓冲区混合实现背景特效；以输出画布捕获轨道替换 WebRTC 视频生产者，保证会议连接连续；以状态机方式处理屏幕共享、设备切换、背景切换和会议退出。

从实际应用目的看，本发明旨在降低会议系统服务端算力压力，减少用户真实背景画面上传带来的隐私风险，提高浏览器端背景特效处理的实时性和稳定性，并提升会议中启停特效、切换背景、屏幕共享和设备切换时的用户体验。

从技术改进目的看，本发明针对现有技术中成本高、响应速度慢、边缘效果差、使用不方便、媒体流切换不稳定和资源释放不彻底等问题，提出了一种更适合 Web 实时会议系统的端侧视频流特效处理方法。该方法能够在不依赖专用客户端、不要求服务端执行背景合成、不破坏现有 SFU 转发架构的前提下，使背景虚化和背景替换功能进入可持续运行的工程状态。

因此，申请本发明的目的在于明确并保护上述端侧视频流特效处理链路中的技术特征、模块组合和状态控制方法，防止研发成果被简单复用或拆分规避，同时为后续产品化、论文成果转化和知识产权布局提供基础。
